Vexum is configured by environment variables, set in `deploy/compose/.env` for Docker Compose (seeded
from `.env.example` on first `make all`). Defaults below are what the stack falls back to when the
variable is unset — fine for local evaluation, **not** for anything exposed.

<Warning>
Change every secret (`ADMIN_TOKEN`, `INTERNAL_API_SECRET`, DB and MinIO credentials,
`VEXA_DISPATCH_SIGNING_KEY`, `NEXTAUTH_SECRET`) before putting the stack on a network. The defaults
are public.
</Warning>

## The config contract (`config.v1`)

Every service declares its configuration in a sealed `config.v1` declaration (schema at
`deploy/contracts/config.v1`), in three classes:

- **required-explicit** — missing at boot fails the service loudly with a `ConfigError` naming
  **every** missing key at once (e.g. meeting-api's `ADMIN_TOKEN`).
- **defaulted** — a documented code default applies when unset.
- **capability** — an optional feature with a tri-state you can read off the service's `/health`:
  `configured` / `not_configured` / `misconfigured`. Some capabilities carry a **live probe**
  (an HTTP call or a file check) that runs at boot and lazily on `/health`; a failing probe
  demotes the row to `misconfigured` with a reason. Capability states never degrade the process
  `status` — they gate the endpoints that need them, with a typed `503` naming exactly which
  variables to set.

```bash
curl -s http://localhost:18080/health | jq .capabilities
# { "stt": { "state": "configured", "probe": { "ok": true, "kind": "http" } },
#   "object_storage": { "state": "configured" } }
```

So the first move when a feature misbehaves is always: **check the owning service's `/health`
capability rows** — meeting-api for `stt` and `object_storage`, runtime and agent-api for
`model_inference`.

## Transcription (STT)

| Variable | Default | Purpose |
|---|---|---|
| `TRANSCRIPTION_SERVICE_URL` | — | STT service **base URL** (the client appends `/v1/audio/transcriptions`), e.g. `http://<gpu-host>:8083`. Point it at the bundled service you deploy separately (`deploy/transcription`) or a hosted endpoint. |
| `TRANSCRIPTION_SERVICE_TOKEN` | — | STT auth token — must match the `API_TOKEN` of your `deploy/transcription` unit, or a token from `vexa.ai/account`. |
| `TRANSCRIBE_ENABLED` | `true` | Deployment-wide default for `transcribe_enabled` on `POST /bots`. Set `false` for a deliberately STT-less deployment that spawns **capture-only** bots instead of rejecting every spawn. |
| `RECORDING_ENABLED` | `true` | Deployment-wide default for `recording_enabled` on `POST /bots`. |

The STT service is the **GPU workload, deployed separately** from this stack — see
[Deployment → Transcription](/deployment#transcription-the-separate-gpu-unit). The main stack
stays GPU-free and reaches it over the network via the two variables above.

**How STT misconfiguration surfaces** (fail-loud, not silent):

- **Unset** — `POST /bots` with transcription requested is rejected **at spawn** with `503`:
  `transcription requested but the STT service is not configured (config.v1 capability 'stt' is
  not_configured: TRANSCRIPTION_SERVICE_URL, TRANSCRIPTION_SERVICE_TOKEN unset) — set them, or
  spawn with transcribe_enabled=false`. No bot joins just to produce dead air.
- **Set but rejected** (expired/wrong token) — the `stt` capability's **live HTTP probe** posts to
  `TRANSCRIPTION_SERVICE_URL/v1/audio/transcriptions` with your token; a `401`/`403` or an
  unreachable host shows as `stt: misconfigured` (with the reason) on meeting-api's `/health`.
  Without the probe, a rejected token is the worst failure mode in the stack: bots join,
  meetings run, and every transcript comes back empty.
- **Opting out explicitly** — per-spawn `"transcribe_enabled": false`, or deployment-wide
  `TRANSCRIBE_ENABLED=false`.

### Recording storage backends

Recordings go to **any S3-compatible object store** through one client; the bundled MinIO is just
the default target. Resolution order (first set wins):

| Setting | Resolved from | Default |
|---|---|---|
| endpoint | `S3_ENDPOINT` (full URL) → `MINIO_ENDPOINT` (`host:port`) + `MINIO_SECURE` | `http://minio:9000` |
| credentials | `S3_ACCESS_KEY` / `S3_SECRET_KEY` → `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` | MinIO defaults |
| bucket | `MINIO_BUCKET` → `RECORDING_BUCKET` | `vexa` |
| `STORAGE_BACKEND` | metadata **label** stamped into each recording's stored metadata — not a behavior switch | `minio` |

To use AWS S3 (or any other S3-compatible store): set `S3_ENDPOINT`, `S3_ACCESS_KEY`,
`S3_SECRET_KEY`, point the bucket variables at your bucket, and set `STORAGE_BACKEND=s3` so the
recording metadata says where the bytes live. The `object_storage` capability row on meeting-api's
`/health` reports whether a store is configured.

## Model inference — the provider matrix

Two things consume a model, configured independently:

1. **The completion port** (`VEXA_LLM_*`) — provider-agnostic chat completions used by the
   meeting copilot's card beats. Bring any endpoint; no inference has to leave your network.
2. **The agent harness** (`VEXA_RUNNER`, default `claude-code`) — the CLI coding agent that runs
   workspace turns (chat / routines / post-meeting docs). It authenticates from the
   **model credentials** below, not from `VEXA_LLM_*`.

### `VEXA_LLM_PROVIDER`

| Provider | Needs | Notes |
|---|---|---|
| `openai-compat` (default) | `VEXA_LLM_BASE_URL` (**required — there is no default host**), `VEXA_LLM_MODEL`, `VEXA_LLM_API_KEY` (optional for local runtimes) | Works with OpenRouter, Ollama, vLLM, LM Studio, OpenAI — any `{base}/chat/completions` endpoint. |
| `anthropic` | `VEXA_LLM_MODEL`, `VEXA_LLM_API_KEY`; `VEXA_LLM_BASE_URL` defaults to `https://api.anthropic.com` | Speaks the Messages dialect. |
| `claude-cli` | mounted/brokered Claude **subscription credentials** (below) — no API key | Beats ride the claude CLI; slower, for subscription-only deployments. |

Key/URL fallbacks: `VEXA_LLM_API_KEY` → `ANTHROPIC_AUTH_TOKEN` → `ANTHROPIC_API_KEY`;
`VEXA_LLM_BASE_URL` → `ANTHROPIC_BASE_URL` (openai-compat only).

**What each misconfiguration produces** (typed, fail-loud):

| Misconfiguration | Error |
|---|---|
| `openai-compat` without a base URL | `LLMConfigError: no completion endpoint: set VEXA_LLM_BASE_URL …` |
| no model resolvable at call time | `LLMConfigError: no model: set VEXA_LLM_MODEL …` |
| endpoint rejects the key (`401`/`403`) | `LLMAuthError: <status> from <base_url>: <response>` |
| unknown provider value | `LLMConfigError: unknown VEXA_LLM_PROVIDER '…' — known providers: ['anthropic', 'claude-cli', 'openai-compat']` |

| Variable | Default | Purpose |
|---|---|---|
| `VEXA_LLM_PROVIDER` | `openai-compat` | `openai-compat` · `anthropic` · `claude-cli`. |
| `VEXA_LLM_BASE_URL` | — (`https://api.anthropic.com` for `anthropic` only) | Completion endpoint base URL. |
| `VEXA_LLM_API_KEY` | — | Endpoint credential (fallbacks above). |
| `VEXA_LLM_MODEL` | — | Deployment-default model id. |
| `VEXA_LLM_MAX_TOKENS` | `4096` (anthropic) | Max tokens per completion. |
| `VEXA_MODEL_ALLOWLIST` | — (allow any) | Comma-separated gate on workspace-pinned models. |
| `VEXA_RUNNER` | `claude-code` | The agent harness adapter (only option today). |
| `VEXA_AGENT_MODEL` | — | Model for agent workspace turns (overrides `VEXA_LLM_MODEL`). |
| `VEXA_MEETING_MODEL` | — | Model for meeting-time card beats (overrides `VEXA_LLM_MODEL`). |
| `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_BASE_URL` | — | claude-code harness credentials; also the `VEXA_LLM_*` fallbacks. |
| `ANTHROPIC_MODEL` · `ANTHROPIC_DEFAULT_OPUS_MODEL` · `…_SONNET_MODEL` · `…_HAIKU_MODEL` | — | Per-tier model overrides brokered into workers. |
| `VEXA_AGENT_DEFAULT_SUBJECT` | `u_live` | Fallback subject before the gateway fronts agent-api. |

## Model credentials on each deploy target

Agent workers are **spawned on demand** — the credential has to reach the worker, and the
mechanism differs per [runtime backend](/core/runtime). The `model_inference` capability row on
the runtime's and agent-api's `/health` tells you whether a credential path is in place
(`mode=any`: any one of `HOST_CLAUDE_CREDENTIALS` / `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` /
`VEXA_LLM_API_KEY` counts as configured).

### Compose / `RUNTIME_BACKEND=docker`

Two paths — configure exactly one:

- **Subscription credentials file** — set `HOST_CLAUDE_CREDENTIALS` to a path **on the Docker
  host** (typically `$HOME/.claude/.credentials.json` after `claude login` on the host). The
  runtime bind-mounts that file **read-only** into every spawned agent-worker at
  `/root/.claude/.credentials.json`; the worker's claude CLI authenticates from it. No key
  material passes through env.
- **API key via env** — leave `HOST_CLAUDE_CREDENTIALS` empty and set `ANTHROPIC_API_KEY` or
  `ANTHROPIC_AUTH_TOKEN` (+ `ANTHROPIC_BASE_URL` for a gateway/OpenRouter); the runtime brokers
  those into workers as environment.

<Warning>
**The docker mount pitfall:** if `HOST_CLAUDE_CREDENTIALS` points at a path that doesn't exist,
Docker creates it as an **empty directory** inside the worker, and the worker's claude CLI
fails at chat time with `Model inference failed: Not logged in`. The same path is mirror-mounted
into the runtime container so its config.v1 **file probe** catches this early: a bad path shows as
`model_inference: misconfigured` (reason `directory` / `unreadable` / `non-json`) on the
runtime's `/health` before anyone opens a chat.
</Warning>

### Kubernetes / `RUNTIME_BACKEND=k8s`

There is no host file to mount — worker Pods get credentials as **environment stamped into the
dispatch spec** by agent-api, from an explicit allowlist (`CLAUDE_CODE_OAUTH_TOKEN`,
`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `VEXA_LLM_API_KEY`,
`VEXA_LLM_BASE_URL`; nothing outside the list crosses). `CLAUDE_CODE_OAUTH_TOKEN` is the claude
CLI's subscription OAuth token — the env twin of the docker credentials mount. Deliver the values
onto **agent-api** via the chart's Secret machinery — see [Helm](/deployment/helm#model-credentials).

<Note>
The k8s passthrough lands with **PR #52** (`fix/worker-model-auth-passthrough`). Before it, the
chart wired `ANTHROPIC_*` onto the long-running deployments but the credentials never crossed
into worker Pods — chat failed with `Not logged in`.
</Note>

### Lite / `RUNTIME_BACKEND=process`

Everything runs in one container, so credentials are plain container env (`-e ANTHROPIC_API_KEY=…`
/ `-e CLAUDE_CODE_OAUTH_TOKEN=…` on `docker run`, or via the repo-root `.env` with `make lite`);
workers are child processes spawned through the `vexa-agent-worker` launcher and inherit them.
See [Vexa Lite](/deployment/lite#model-credentials).

**Precedence:** if both a subscription credential and `ANTHROPIC_*` env are set, the claude CLI
prefers env-based auth over the mounted `~/.claude/.credentials.json`. Configure exactly one path.

## Images & runtime

| Variable | Default | Purpose |
|---|---|---|
| `IMAGE_TAG` | `dev` | Tag for the built service images. |
| `BROWSER_IMAGE` | `vexaai/vexa-bot:v012` | Browser/bot container the runtime spawns per meeting. **Built from source** (`make bot`), spawned without pulling — the published `vexaai/vexa-bot:dev` is the old 0.10 line and is incompatible. |

| `BOT_SIGTERM_GRACE_MS` | `20000` | Bot-side force-exit watchdog inside the SIGTERM window — must fit under the runtime grace. *(Lands with PR #50.)* |
| `LOG_LEVEL` | `info` | Log verbosity. |

The gateway (`:18056`) is the one front door; the terminal web workbench is at `:13000`. The other host
ports above are bound to `127.0.0.1` for local inspection and aren't needed for day-to-day use.
</Note>
