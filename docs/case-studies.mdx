title: "Failure case studies"
description: "Three real incidents from the 0.12 release hardening — and the machinery that now prevents each class."
---

These are not marketing stories. Each is a real incident found while release-testing 0.12 on
fresh infrastructure, kept here because the *mechanism it motivated* is what you'll actually
lean on when operating the stack. Pattern in all three: **a config or lifecycle fault that
produced no evidence** — the fix in every case is machinery that makes the failure loud and
attributable.

## 1 · The rejected STT token — silent transcript-less meetings

**Symptom.** Bots joined fine, meetings ran, recordings landed — and every transcript came back
empty. No error anywhere: `POST /bots` returned `201`, `/health` said `ok`.

**Root cause.** `TRANSCRIPTION_SERVICE_TOKEN` was set but **rejected** (`401`) by the STT
service it pointed at. The transcription client's auth failure happened per-request, deep in the
audio path, and surfaced to no one. A *set-but-wrong* credential is strictly worse than an unset
one — the unset case at least looked unconfigured.

**The mechanism now.** The `config.v1` contract gives every service declared **capabilities with
live probes** ([Configuration](/configuration#the-config-contract-configv1)): meeting-api's
`stt` capability probes the real endpoint with your real token and reports
`misconfigured` (with the reason) on `/health`; an unset STT rejects the spawn itself with a
typed `503` naming the exact variables. The same incident on the credentials side (a dangling
`HOST_CLAUDE_CREDENTIALS` path that Docker silently turns into an empty directory) is caught by
the `model_inference` file probe.

## 2 · Runtime restart orphaned live bots — a ghost attendee

**Symptom.** After a runtime restart, a bot from before the restart kept sitting in a meeting —
recording — with the control plane convinced the meeting was over. `DELETE /bots` couldn't reach
it; the participant list showed an attendee nobody could stop.

**Root cause.** The restarted runtime had **amnesia**: it only knew workloads it had spawned
since boot. Worse, the meeting lifecycle treated the runtime's `404` ("I don't know that
workload") as evidence the bot was *gone* — so the meeting advanced to a terminal state while
the real container ran on.

**The mechanism now** (PR #50). Workloads carry adoption labels, and the runtime **re-adopts**
still-live containers/Pods on boot — including exited ones, adopted with their real exit code as
evidence. The lifecycle is now **evidence-based**: an untracked-workload `404` is never treated
as termination; only a tracked terminal state or the bot's own callback advances the FSM, and a
stop isn't "done" until termination is confirmed (unconfirmed stops stay `stopping`, loudly,
and are retried). The bot itself now handles SIGTERM with a graceful leave inside a bounded
grace window (`RUNTIME_STOP_GRACE_SEC` / `BOT_SIGTERM_GRACE_MS`).

## 3 · Transcripts that were never saved — 2 meetings permanently lost

**Symptom.** After a night of test meetings with perfectly good *live* transcripts, the
`transcriptions` table held **zero rows** — and for the older meetings the redis hashes had
already expired. Those transcripts are gone permanently.

**Root cause.** The 0.12 carve ported the segment consumer, the read-path merge, and the store —
but **never the 0.10 background db-writer** that moved segments from redis to postgres. Live
reads worked (redis), so nothing looked wrong until redis forgot.

**The mechanism now** (PR #53, ruled a **regression fix**, not a feature). The db-writer loop is
restored with the parent's exact semantics — flush settled segments, trim redis *only after* the
confirmed write, finalize everything at meeting completion — plus durable processed-notes views
and per-send session keying. The regression test is the incident inverted: flush, wipe redis,
and assert `GET /transcripts` still serves. See
[Transcript persistence](/architecture/transcript-persistence).

---

**The operating lesson** we took from the night: the same config class must behave identically
on every deploy target (the STT gap was hit on compose, lite, *and* helm, sequentially). That's
now a release-line discipline — capability rows are compared across the compose/lite/helm
validation stacks, and a config fix on one target is swept across all of them.
