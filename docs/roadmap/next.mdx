Two tiers, kept honest: **committed** means the maintainer has ruled it and it has a target;
**direction** means we know where we're heading but not when each piece lands. How we work while
getting there is the [decisions register](/decisions); current proven state is
[Status](/roadmap/status).

## 0.12.1 — the fast-follow (committed, days not months)

- **Speaker attribution on Teams and Zoom** — the known regression in 0.12.0
  ([changelog](/changelog)): the capture kit's speaker binding is wired for Google Meet only, so
  Teams/Zoom segments carry provisional `seg_N` labels. The detection machinery exists in the
  meeting modules (previously proven) — this is integration, not research. Maintainer ruling:
  ships next release, with a live verify pass per platform.
- **Mount the transcript share surface** — `POST /transcripts/{platform}/{native}/share` +
  `GET /public/transcripts/{share_id}.txt` are sealed in `api.v1` but not mounted in 0.12.0.
  Visitor access via short-lived capability URLs; deliberately the
  [stepping stone](/roadmap/multi-workspace#the-stepping-stone-visitor-transcript-access) to the
  invite/membership flow.
- **config.v1 probe follow-ups** — move live probes off the event loop; give lite its own
  `model_inference` capability row.
- **Capability-parity release check** — a release-pipeline leg that diffs the `/health`
  capability rows across the compose/lite/helm validation stacks; any asymmetry fails the
  release ([fix the class, not the instance](/decisions#fix-the-class-not-the-instance)).

- **Docs verification sealing** — extend the seal culture to the corpus, three tiers:
  (1) *generate* the highest-drift references from their machine truths — the API reference
  renders from the sealed `api.v1` OpenAPI, the configuration tables from the `config.v1`
  declarations — generated pages cannot drift by construction; (2) *`gate:docs`* — both-ways
  coverage and existence checks in the `gate:config-contract` style (every declared key/sealed
  capability has a page; every key or endpoint mentioned in MDX exists in the declarations/sealed
  spec; links and nav resolve), mutation-tested; (3) *source-coupled freshness seal* — each page
  declares the tree paths it documents (`sources:` frontmatter) and the commit it was verified
  against, recorded in `docs.seal.json`; the gate goes red when a page's sources change without
  the page acknowledging it. Prose truthfulness (tier 4) is not gate-able: a scheduled
  adversarial docs-review routine probes recently re-sealed pages against the tree. The 0.12.0
  corpus (tree-verified at review time) is the sealing baseline.

## The 0.12.x arc (committed features, sequencing open)

- **Interactive bots** — in-meeting chat, screen share, avatar; the endpoints are contract-sealed
  today, unmounted ([parity table](/changelog#not-yet-in-012)).
- **`discord` ingest + participants endpoint** — return with the next `api.v1` contract
  revision.
- **Zoom authorized-join** — bring-your-own OBF/ZAK tokens and/or the native SDK path, restoring
  parity with the 0.10 Zoom track (0.12.0 joins via the web client only).
- **MCP behind the gateway** — one MCP server for all of Vexa's capabilities, mounted at the
  gateway; the standalone port is interim ([MCP server](/api/mcp)).
- **Community-issue triage** — the full community backlog is triaged post-release, verdict by
  verdict, per the [community-steering policy](/decisions#community-steering).

## Direction: multi-workspace collaboration

The accepted architecture — required per-user system workspaces, sharing as membership via
scoped invite tokens, agent-mediated merge for ~20 concurrent participants on a live shared
meeting workspace, humans-only attribution — is documented on its own page:
[Multi-workspace direction](/roadmap/multi-workspace). Current storage shapes already honor its
constraint (transcripts and processed views are addressable, multi-consumer artifacts). The
design doc is chartered after v0.12.0; no shipping date is claimed.
