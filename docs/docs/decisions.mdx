This is the register of durable project policies. Every entry was explicitly ruled by the
maintainer (dates given), and where a decision has an enforcing artifact — an ADR, a gate, a
contract — it is linked. Direction (where the product goes) lives on the
[roadmap](/roadmap/next); this page is *how* we work while getting there.

## Repository boundaries (2026-07-03)

`Vexa-ai/vexa-core` is the FINOS open-core project. Development happens on the working repo's
release branches; content flows into vexa-core through the **carve train** — a manifest-driven,
authorship-preserving replay (merge commits only, never squash). No ad-hoc PRs to vexa-core;
exceptions are owner-driven and deliberate. *Why:* one governed public core, one place where
work actually happens, deterministic convergence between them. — ADR-0025
(`docs/adr/0025-repo-boundaries-and-bidirectional-sync.md`).

## Humans-only authorship (2026-07-04)

Anything pushed to GitHub carries a **human git author** — the operating maintainer — never a
machine identity. AI contribution is acknowledged as a trailer, never as author; machine
identities are mailmapped to the operating maintainer. (Runtime-internal workspace git, where
the platform is the committer, is exempt.) *Why:* accountability and provenance — a human
answers for every change.

## Community steering (2026-07-04)

Community bugfixes and clean opt-in features **merge, with credit**. Salvageable work in a stale
PR is cherry-picked with the original author preserved. Only design-value-dead code is closed —
and always with a personal note explaining why, or crediting what the idea contributed. *Why:*
contributors are the project's future maintainers; nobody's work is silently discarded.

## The config contract — config.v1 (2026-07-04)

All deployment configuration is **declared**: every service ships a sealed `config.v1`
declaration (required-explicit / defaulted / capability classes), boot preflight fails loudly
naming every missing key, capabilities are tri-state rows on `/health` with live probes, and
`gate:config-contract` enforces declaration ↔ deploy-surface ↔ code-read agreement in both
directions. *Why:* an undeclared config knob is a silent failure waiting for a deploy target to
find it. — ADR-0026, [Configuration](/configuration#the-config-contract-configv1), PR #49.

## Fail loud, with evidence (2026-07-04)

No state transition without evidence, no capability failing silently. A runtime `404` is
"untracked", never proof a workload is gone; a stop isn't done until termination is confirmed; a
misconfigured credential shows up on `/health`, not as empty output hours later; a spawn that
can't do what was asked is rejected with a typed error naming the fix. *Why:* the release
hardening showed every painful incident was a **silent** fault — see the
[case studies](/case-studies). — PRs #49/#50/#53.

## Fix the class, not the instance (2026-07-05)

A configuration fix discovered on one deploy target is **immediately swept across all targets**
(compose, lite, helm), and capability parity across the three validation stacks is a release
check. *Why:* the same STT-wiring gap was hit on all three targets, sequentially, in one night —
repeating a same-class failure across targets is treated as a process violation, not bad luck.

## Docs along the way (2026-07-05)

Every PR carries its own documentation (env comments, ADRs, chart docs), and **`docs/` is the
corpus** — one flat, published documentation tree; no shadow doc piles. Every doc claim is
verified against the tree or a live probe, never inferred from planning documents. *Why:* docs
that trail the code are wrong docs; the corpus is only trustworthy if writing it is part of
shipping.

## Releases ship against an explicit DoD (2026-07-04)

A release has a written definition of done: all images published and referenced, all PRs/issues
resolved, every deploy target proven **from the published images on fresh infrastructure**, the
maintainer **personally eyeballs** the client on each target and live meetings on the real
platforms, backward compatibility validated behaviorally, core parity re-checked, docs updated.
*Why:* "CI is green" is not "it works" — the release-eyeball pass caught defects every automated
leg missed.

## No migrations on a release line (2026-07-05)

Fixes landing inside a release line must not require schema migrations — extension happens
inside existing structures. *Why:* operators on a release line get fixes, not upgrade
ceremonies. Corollary: **`meetings.data` JSONB is the extension point** — recordings, notes, and
processed views (`data.processed.views[]`) live there as addressable, versioned artifacts,
which also keeps them multi-consumer for the
[multi-workspace direction](/roadmap/multi-workspace). — PR #53,
[Transcript persistence](/architecture/transcript-persistence).
