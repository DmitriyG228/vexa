---
title: "Connect a GitHub repo"
description: "Attach any GitHub repository as your workspace — public or private — and work on it with the agent."
---

Your workspace is a git repository ([workspace.v1](/concepts#workspace)) — and it doesn't
have to be the seeded one. You can attach **any external git repo**, including a private
GitHub repository, as your active workspace. The agent then reads, writes, and commits
into that repo's checkout on every turn.

## From the terminal

Open the **Workspace** surface → the workspace switcher → **Attach a repo**. The form takes:

- **Repo URL** — e.g. `https://github.com/your-org/your-repo`
- **Ref** — branch or tag (default `main`)
- **Access token** — only for private repos: a GitHub fine-grained PAT with read access.
  The token is used server-side **for the clone only and never stored**; error messages
  are token-redacted.

## From the API

```bash
curl -X POST "$AGENT_API/api/workspace/swap" \
  -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"repo": "https://github.com/your-org/your-repo", "ref": "main", "token": "github_pat_..."}'
```

The response tells you what happened: `cloned: true` on first attach, and which slug your
previous workspace was **parked** under.

## Nothing is ever destroyed

Attaching is a **swap**, not a replacement:

- Your current workspace is *parked* — kept intact, invisible to the workspace tree,
  ready to swap back to.
- Swapping back to a parked workspace (or to the seed: pass `"repo": null`) restores it
  **without a re-clone** — every local change and agent commit made while it was active
  is still there.
- `GET /api/workspace/attached` lists the active workspace and all parked slots.

## What the agent does with it

Every agent turn runs over the attached checkout and **commits its changes** — the
workspace is the agent's durable memory, so your repo's clone accumulates the work
with full git history. Commits are attributed per the
[authorship principles](/decisions#humans-only-authorship).

## Pushing back to GitHub

Turn commits land in the platform's server-side clone of your repo. Pushing them back
to GitHub is a **governed action**: the push adapter uses per-user brokered credentials
(the token lives on the remote only for the duration of the push, then is scrubbed), and
push flows are part of the [proposal-gated VCS direction](/roadmap/next) — write access
to your repos always crosses an explicit gate, never happens as a side effect.
## Syncing with GitHub

What syncs when, in 0.12.0:

| Direction | How | When |
|---|---|---|
| Vexa → GitHub | **Publish** (first time) / **Push updates** (after) on the workspace row | on demand — plain fast-forward push, never force |
| GitHub → Vexa | not yet automatic — attaching clones **once**; later pushes to GitHub are not pulled | re-attach with *start fresh* to take a new clone (your previous tree is parked, not lost) |
| Your laptop ↔ GitHub | normal git — clone the published repo, pull/push | GitHub is the hub; the vexa workspace is one clone of it |

A governed **Pull from GitHub** action (fast-forward applies; real divergence is merged by the
workspace's agent as an attributed turn — never a force, never a silent overwrite) and opt-in
auto-sync via GitHub webhooks are on the [roadmap](/roadmap/next).

## Publish a vexa-born workspace to GitHub

A workspace that started life inside vexa (seeded from the template, not attached from
one of your repos) carries real git history from day one. *Publish* gives it a home on
GitHub: vexa creates the repository under your account and pushes the workspace's full
history to it.

In the terminal, open **workspaces** in the sidebar and choose **Publish to GitHub…**
(shown when your active workspace is vexa-born). Fill in:

- **Repo name** — defaults to your workspace's name.
- **Private** — on by default; untick to create a public repository.
- **GitHub token** — a personal access token with `repo` scope. It is used once,
  server-side, to create the repository and push — it is never stored.

On success the repository URL is shown. Publishing again later pushes your new commits
to the same repository (a plain fast-forward push — vexa never force-pushes; if the
remote has diverged you get a clear error instead).

Notes:

- To publish into a repository you already created (it must be empty), or under an
  organization, call the API directly: `POST /api/workspace/publish` with
  `{"remote_url": "https://github.com/you/repo.git", "token": "…"}` or
  `{"repo_name": "…", "org": "your-org", "token": "…"}`.
- If the name is taken you get a clear error — pick another name, or pass the existing
  repository's URL as `remote_url` to push into it.
- A workspace **attached** from one of your own repos can't be published — it already
  has an origin; push there instead.
